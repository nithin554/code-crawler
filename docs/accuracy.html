A 0.00 bucket is not a low-confidence guess: it is the unresolved marker the crawler writes when it cannot prove a receiver, such as __unknown__:this.repository.save. Filtering it out is the honest way to read a call graph.

Runtime proof: dispatch edges against a real call log

One edge type is checked by running code instead of reading it.

DYNAMIC_DISPATCH is the edge type where static reading is most likely to be wrong: the call site names an interface method, and the target is whichever implementation happens to be live at that moment. So it is verified against execution. A fixture defines an interface Shape with three implementations (Circle, Square, Triangle); Main builds a Circle and a Square, never a Triangle, and drives all of them through the interface. Every implementation prints a line when its method actually runs, so the log is a real call log rather than a second reading of the source.

npm run bench:runtime compiles the fixture with javac, runs it, crawls the fixture directory, and reconciles the two.

Source Target Confidence Proven by execution
fixture.Shape#area fixture.Circle#area 0.80 yes
fixture.Shape#area fixture.Square#area 0.80 yes
fixture.Shape#area fixture.Triangle#area 0.80 no — never constructed
The third edge is not a false positive, and the benchmark does not score it as one. Triangle really does implement Shape, so the edge becomes true the moment any code constructs a Triangle; this particular run simply never did. Counting it as an error would understate the graph, and counting it as proven would overstate it, so it is reported separately as unexercised. That over-approximation is exactly why DYNAMIC_DISPATCH carries a flat 0.80 rather than a near-1.00 confidence: the edge set is deliberately a superset, and a single-implementation interface gives that superset nothing to add while an interface with many implementations gives it plenty.
What this proves, and what it does not. It proves soundness for the dispatch edges it exercises: every method the graph claims is reachable through the interface, and which actually ran, is an edge the graph contains. It does not turn the precision and recall numbers above into runtime measurements — those four projects are still hand-verified, and the Spring and NestJS wiring (routes, injection, proxy boundaries) is not exercised by this fixture at all. There is no Java agent here, only observable side effects in a five-class fixture. Treat it as one edge type verified deeply, not the whole graph verified broadly.

Where Code-Crawler is weak

Reproduced from the benchmark failures, in order of how much they cost you.

1. FastAPI router prefixes are dropped

APIRouter(prefix="/items") is ignored, so @router.get("/") is reported as / instead of /items/. Every route from a prefixed router is wrong in its path while still being emitted, which is the most dangerous shape of error: present, plausible and incorrect. All 8 route misses left in this benchmark are this one defect, and it is the only reason Python recalls worse than Java. The login router, whose decorators spell out full paths, is correct, which isolates the cause. Routes derived from a router prefix must be joined, and the trailing slash is significant in FastAPI.

2. FastAPI dependency aliases produce no INJECTS edge

The template declares its dependencies once as module-level aliases — SessionDep = Annotated[Session, Depends(get_db)] — and then names them in each handler signature. A parameter typed only by such an alias yields nothing, and neither does a dependency reached only through another dependency function. All 5 remaining injection misses are this one case; constructor injection in the two Spring projects is now modelled and scores 1.000. Call resolution still succeeds from inside the handler body, so get_callers and trace_path mostly keep working; what is lost is any query whose answer depends on the wiring edge itself.

3. INJECTS and ROUTES have no confidence model

Both edge kinds are written without a confidence value, so a consumer cannot tell a proven mapping from a derived guess. The project rule is that no edge type exists without a confidence model; these two are the standing exceptions. Recall has improved enough that this now matters more, not less: a Spring @GetMapping on a bean and a Lombok-derived constructor parameter are different strengths of evidence, and the graph reports both with no confidence at all.

4. Dispatch is matched by name and arity, not by proof

A virtual dispatch edge carries a flat 0.80 and is emitted to every in-project subtype with a same-named, same-arity method. It is correct on the sampled labels, but that is partly because spring-boot-realworld's ArticleRepository has exactly one implementation. With several implementations, or overloads differing only by generics, the constant would overstate certainty. There is also no dispatch for lambdas or method references.

5. Foreign calls are unresolved by design

Calls into framework or library types resolve to an ext: node or to an __unknown__ marker, for example Repository<ArticleEntity>.save in the NestJS project. This is the correct trade — the tool does not have TypeORM's bytecode — but it means the graph stops at the framework boundary. Event, messaging and proxy wiring that crosses that boundary is not modelled at all.

What the benchmark already found

Writing the first fixtures exposed a parser crash that silently deleted files. A lookup into a method table was resolving identifiers through Object.prototype, so any file containing a call to toString(), valueOf() or hasOwnProperty() threw during parsing. The crawler records parse failures per file, so those files vanished from the graph with only a log line.

On spring-petclinic this had hidden 7 of 50 files, including the Owner JPA entity: files parsed went from 43 to 50, CALLS edges from 574 to 1,426, and total edges from 1,408 to 2,637. The bug is fixed and covered by regression tests.

The Spring route cases failed on a missing feature rather than a bug. The framework descriptor declared the mapping annotations as entry points, but the Java parser never produced route registrations, so no controller could yield a ROUTES edge at all.

Spring mappings are now extracted: a class-level @RequestMapping prefix is joined with each verb annotation, covering the array form @GetMapping({"/vets"}), a named path = attribute, a bare annotation that inherits the class path, paths without a leading slash, and method = RequestMethod.PUT on the prefix-less form. ROUTES recall went from 0.325 to 0.800, with no invented edge.

Injection failed the same way: the parser only recorded a parameter when an annotation asked for it. Spring has not needed one since 4.3 — the sole constructor of a bean is autowired silently — and a Lombok @AllArgsConstructor leaves the constructor out of the source entirely, so there was nothing to annotate in the first place.

Bean stereotypes now mark a class as container-managed, and its dependencies follow from that: the sole constructor's parameters when there is exactly one, the promoted fields when a Lombok annotation generates the constructor. The rules stay conservative in the ways that matter. Two unannotated constructors inject nothing, because Spring cannot choose between them either. A field initialised at its declaration is skipped. A class with no stereotype is skipped, since no container constructs it. A class that writes its own constructor alongside a Lombok generator injects nothing, because that is two constructors and the same ambiguity applies. Trusting a generator's field list blindly would have produced 0.95-confidence edges to dependencies the code never receives. INJECTS recall went from 0.133 to 0.667, Java recall from 0.778 to 1.000, and precision held at 1.000 with no invented edge.

Reproduce it

One command. No services, no credentials, no database server.

shell
git clone https://github.com/nithin554/code-crawler
cd code-crawler
npm ci
npm run bench:accuracy
npm run bench:runtime

The runner clones each project into a gitignored benchmarks/.cache/ at the commit in benchmarks/manifest.json, crawls it into an in-memory SQLite database, scores the labelled cases and writes benchmarks/reports/accuracy.md and accuracy.json. It exits non-zero when precision or recall drops below the floors in the manifest, and CI runs it on every pull request, so an accuracy regression fails the build. bench:runtime is the separate dispatch proof described above: it needs a JDK 17 or newer (javac on PATH) and writes benchmarks/reports/runtime.md. CI installs Temurin 21 for it.

Thresholds in the manifest are ratchets, not targets: they sit at the value last measured. Raise them when a measurement improves. Precision floors are 1.000, because a confidently wrong edge is worse than a missing one.
