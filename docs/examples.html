The fixture project

An interface with two implementations, a service that calls it, an aspect that intercepts it, and a class carrying framework decorators.

Payment.java · Checkout.java 
public interface Payment {
    void pay(double amount);
}

public class Checkout {
    private final Payment payment;

    public Checkout(Payment payment) {
        this.payment = payment;
    }

    public void checkout(double amount) {
        payment.pay(amount);   // which pay()?
    }
}
AuditAspect.java · DecoratedService.java 
@Aspect
public class AuditAspect {
    @Pointcut("execution(* com.acme.*.pay(..))")
    public void paymentCall() {}

    @Around("paymentCall()")
    public Object auditPayment(JoinPoint jp) { ... }

    @Before("execution(* com.acme.Checkout.checkout(..))")
    public void beforeCheckout() {}
}

@Service
public class DecoratedService {
    @Transactional(readOnly = true)
    @Cacheable("orders")
    public String describe(String id) { ... }
}

Index it with crawl_project({ path: ".../tests/fixtures/java/dynamic" }). The crawl reports 6 files, 43 nodes, 61 edges, 2 dynamic-dispatch edges, and 4 advice edges. Response bodies below are trimmed to the fields that matter.

Example 1

Impact analysis: who reaches this method?

Before changing Payment#pay, ask for every caller — including virtual-dispatch and advice callers that a text search misses.

request 
get_callers({
  symbol: "com.acme.Payment#pay",
  transitive: true,
  include_dynamic: true,
  include_advice: true
})
response 
{
  "target": {
    "id": "com.acme.Payment#pay",
    "kind": "method",
    "filePath": "com/acme/Payment.java"
  },
  "callers": [
    {
      "caller": {
        "id": "com.acme.AuditAspect#auditPayment",
        "kind": "method"
      },
      "depth": 1,
      "edgeKind": "ADVISES"
    },
    {
      "caller": {
        "id": "com.acme.Checkout#checkout",
        "kind": "method"
      },
      "depth": 1,
      "callSiteLine": 12,
      "edgeKind": "CALLS"
    }
  ]
}

The advice caller is the important one: changing the signature also breaks AuditAspect#auditPayment, which never mentions pay in its own body.

Example 2

Runtime trace: what actually executes?

trace_execution follows static calls, then fans out across virtual dispatch and weaves advice in as INTERCEPT hops.

request · trace_execution 
trace_execution({
  symbol: "com.acme.Checkout#checkout",
  include_dynamic: true,
  include_advice: true,
  max_depth: 6
})
response · steps 
{
  "root": { "id": "com.acme.Checkout#checkout", "kind": "method" },
  "stepCount": 6,
  "steps": [
    {
      "symbol": { "id": "com.acme.Checkout#checkout" },
      "depth": 0
    },

      "depth": 1,
      "via": "INTERCEPT",
      "callSiteLine": 12

    {
      "symbol": { "id": "com.acme.Payment#pay" },
      "depth": 1,

      "callSiteLine": 12
    },
    {

      "depth": 2,
      "via": "INTERCEPT"
    },
    {
      "symbol": { "id": "com.acme.CardPayment#pay" },

Reading the via field is the whole point: CALLS is what the source says, DYNAMIC_DISPATCH is what the hierarchy allows at runtime, and INTERCEPT is behaviour injected by an aspect.

Example 3

Aspect audit: what intercepts what?

Pointcuts are resolved — named pointcut references, execution, wildcards, and boolean operators all produce concrete ADVISES edges.

request 
find_aspects({ limit: 20 })
response 
{
  "aspectCount": 1,
  "aspects": [
    {
      "aspect": { "id": "com.acme.AuditAspect" },
      "advice": [
        {
          "method": { "id": "com.acme.AuditAspect#auditPayment" },
          "adviceKind": "around",
          "pointcut": "paymentCall()",
          "advised": [
            { "id": "com.acme.CardPayment#pay" },
            { "id": "com.acme.Payment#pay" },
            { "id": "com.acme.UpiPayment#pay" }
          ]
        },
        {
          "method": { "id": "com.acme.AuditAspect#beforeCheckout" },
          "adviceKind": "before",
          "pointcut": "execution(* com.acme.Checkout.checkout(..))",
          "advised": [
            { "id": "com.acme.Checkout#checkout" }
          ]
        }
      ]
    }
  ]
}

Note that @Around("paymentCall()") is reported with the resolved effect — all three pay methods — not just the pointcut name. This is the difference between indexing an annotation and understanding it.

Example 4

Decorators: runtime semantics attached to code

Annotations are graph nodes, so you can find every symbol carrying one — or list everything attached to a single type and its members.

find_annotated 
find_annotated({
  annotation: "Transactional",
  kind: "method"
})
response 
{
  "annotation": "Transactional",
  "count": 1,
  "results": [
    {
      "symbol": {
        "id": "com.acme.DecoratedService#describe",
        "kind": "method",
        "filePath": "com/acme/DecoratedService.java"
      },
      "annotation": "Transactional",
      "line": 11,
      "arguments": ["readOnly = true"]
    }
  ]
}
get_decorators · include_members 
get_decorators({
  symbol: "com.acme.DecoratedService",
  include_members: true
})

// decorators: [ { name: "Service", decorator: false } ]
// members[0].symbol.id: "com.acme.DecoratedService#describe"
// members[0].decorators:
//   { name: "Transactional", decorator: true, arguments: ["readOnly = true"] }
//   { name: "Cacheable",     decorator: true, arguments: ["orders"] }

decorator: true marks framework annotations whose semantics are behavioural — caching, transactions, retries, async execution, security. Structural annotations such as @Override or @Service are indexed but not flagged.

Example 5

Hotspots and dead-code candidates

Two ends of the same graph: where the traffic concentrates, and what nothing calls.

find_hotspots · min_fan_in: 1 
{
  "count": 2,
  "hotspots": [
    {
      "symbol": { "id": "com.acme.Payment#pay" },
      "fanIn": 2,
      "fanOut": 0,
      "adviceCount": 1
    },
    {
      "symbol": { "id": "com.acme.Checkout#checkout" },
      "fanIn": 1,
      "fanOut": 1,
      "adviceCount": 1
    }
  ]
}
find_dead_code 
{
  "count": 2,
  "unused": [
    {
      "symbol": { "id": "com.acme.DecoratedService#describe" },
      "reason": "no incoming call, dispatch, or advice edges"
    },
    {
      "symbol": { "id": "com.acme.DecoratedService#" },
      "reason": "no incoming call, dispatch, or advice edges"
    }
  ]
}

DecoratedService is reached by Spring, not by source. This is the canonical false positive: no in-project caller exists, so the method looks dead. Use constructors-inclusive output and knowledge of your framework's entry points before deleting anything.

Composing the primitives

Real questions combine tools. “Is this aspect safe to remove?” becomes find_aspects → get_callers on each advised method → trace_path from the application entry point. “What breaks if I change this interface?” becomes find_implementations → get_callers per override → find_annotated to spot transactional or cached implementations that carry extra contracts.
